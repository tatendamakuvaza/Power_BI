# scripts/ — the data pipeline

Everything in `data/` is generated by these scripts. They are deterministic: the same seed always
produces the same bytes, which is what allows the labs to publish exact expected results.

## The one command you normally need

```bash
python3 scripts/run_all.py
```

It runs, in order: Mhondoro generator → Maxhub generator → churn model → vendor matcher → Excel
workbooks → data dictionary → control-total verification, and stops with a non-zero exit code if a
required step fails.

**Everything is reproducible, not just deterministic.** The CSVs are byte-identical because the seeds
are fixed, and the `.xlsx` workbooks are byte-identical too because the build pins the workbook
metadata and normalises the zip container (openpyxl otherwise stamps files with the current time). A
rebuild therefore leaves Git clean — which is what the CI job asserts.

| Flag | Use |
|---|---|
| `--no-workbooks` | Skip the Excel build (run without installing openpyxl) |
| `--check-only` | Verify the committed data without regenerating anything (used by CI) |

## The scripts

| Script | What it does | Needs |
|---|---|---|
| [`generate_data.py`](generate_data.py) | Builds Mhondoro Manufacturing: 8 dimensions, 9 facts, `MaxhubEngagements.csv` and `InjectionLog.csv` — 13,929 GL lines with seven hidden fraud schemes, deterministic from seed 20251007 | stdlib |
| [`generate_maxhub_data.py`](generate_maxhub_data.py) | Builds Maxhub's own firm data: service-line financials, billable hours, pipeline and the 150-row client churn dataset | stdlib |
| [`ml_churn_model.py`](ml_churn_model.py) | Trains an interpretable logistic regression on the churn data (70/30 split, seed 7) and writes `data/scored/maxhub_client_churn_scored.csv` with `ChurnProbability`, `ChurnRisk`, `PredictedToStay` and `ModelVersion` | stdlib |
| [`fuzzy_match_vendors.py`](fuzzy_match_vendors.py) | Near-duplicate supplier-name matcher for fraud screening: normalises names, blocks, scores pairs and writes candidates to `data/scored/vendor_match_candidates.csv` for review | stdlib |
| [`build_workbooks.py`](build_workbooks.py) | Builds the three Excel workbooks, including the Mhondoro warehouse with `InjectionLog` as a hidden sheet | openpyxl |
| [`build_dictionary.py`](build_dictionary.py) | Writes `data/dictionary/DataDictionary.csv` — every field in every table with its meaning and use | stdlib |
| [`verify_data.py`](verify_data.py) | Control checks: line counts, debits = credits, per-journal balance, flagged anomaly totals, orphan keys, data-quality counts. Exits 1 on failure | stdlib |
| [`run_all.py`](run_all.py) | Runs the whole pipeline in order with a summary | stdlib (+openpyxl for workbooks) |

## What the verification checks (and the values it expects)

| Check | Expected |
|---|---|
| GL lines | 13,929 |
| Total debits = total credits | $122,878,886.54 |
| Flagged anomaly journals / value | 171 / $1,945,536.55 |
| Accounts and vendors referenced by the ledger | all present in the dimensions |
| Journals out of balance | 0 |

`verify_data.py` also previews the anomaly schemes and prints the data-quality counts, so it doubles as
a smoke test after any change.

## Rules for changing anything here

1. **Do not edit `generate_data.py` casually.** Any change shifts the random stream and invalidates every
   published figure in the modules, labs, capstones and README.
2. If you must change it, re-run `verify_data.py`, then re-derive the expected-results tables in
   [`../labs/Lab_Index.md`](../labs/Lab_Index.md), the Key Results tables in the README and the capstones.
3. Keep the generators **stdlib-only** — learners on any machine must be able to run them without a
   Python environment.
4. After any change, run the full pipeline and confirm nothing moved that should not have:
   ```bash
   python3 scripts/run_all.py
   git status --porcelain data/     # empty means regeneration is byte-identical
   ```
   If `data/xlsx/*` or `data/dictionary/*` show as modified, the workbook/dictionary builders have lost
   their reproducibility — check `normalise_zip()` and `stamp()` in `build_workbooks.py`.

## CI

[`.github/workflows/verify-data.yml`](../.github/workflows/verify-data.yml) runs the pipeline on every
push: it regenerates the data, verifies the control totals, then fails the build if the committed data
differs from what the generator produces. That guarantees the expected results in the course material
stay true to the data in the repository.
